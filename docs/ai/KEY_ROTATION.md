## Production rollout

Completed: all five functions use the secret API key for PostgREST; prior logs showed `key_mode: "secret"`; production login/product read, AI Bridge status, and harmless function probes succeeded; served frontend bundle uses the publishable key. A direct production request showed Storage rejects an opaque secret key as a JWT (`Invalid Compact JWS`) and also requires an `Authorization` header. To preserve file downloads, signed URLs, trace Storage, and verified backups, `automation`, `knowledge`, and `scripts/backup-storage.mjs` temporarily send the legacy service-role JWT only to the same project's `/storage/v1/` endpoints while retaining the opaque secret in `apikey`. This is a documented **Desvío**: the legacy key remains a server-side Storage consumer and cannot be disabled safely yet. Supabase's official [S3 authentication guide](https://supabase.com/docs/guides/storage/s3/authentication) documents generated S3 access-key pairs for server-side access; use that path to remove the Storage dependency before disabling legacy keys. The documented flow generates those credentials in the project Dashboard; no supported Management API operation was found in the official docs. A Playwright check of the persistent QA profile redirected to Supabase sign-in, so no S3 key was created. Do not disable the legacy keys until Storage has a working replacement and the extension no longer needs the legacy `anon` key. If any smoke fails after a future cutover, re-enable legacy keys immediately.
